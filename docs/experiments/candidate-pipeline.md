# Phase 5A：大量教材収集の低コスト化（候補収集の仕組みの試行）

- 実施日：2026-10-28
- 目的：数百〜数千件の候補を安く見つけ、深い知識を含む資料を優先して確認できるようにする。大量登録が目的ではない。
- 作ったもの：小さな CLI（`tools/candidates/`）、候補データ（`data/candidates/`）、テスト、この報告。
- 作らなかったもの：バックエンド、DB、常駐クローラー、定期実行、管理画面、AI 推論、検索エンジンの変更。

## 1. 仕組み

### ファイル

| ファイル | 中身 | 誰が書くか |
|---|---|---|
| `data/candidates/sources.json` | 情報源の一覧（取得方法・間隔・発信者名のそろえ方）| 人 |
| `data/candidates/candidates.json` | 候補（一覧で取れたメタデータと、規則による分類）| CLI |
| `data/candidates/reviews.json` | 個別確認の結果（本文を読んだ深さ・採否・理由）| 人・AI |
| `tools/candidates/lib.js` | 正規化・重複検出・分類（ネットワークに触れない関数）| — |
| `tools/candidates/collect.js` | 取得と統合、付け直し、内訳の表示 | — |
| `tools/candidates/candidates.test.js` | テスト（`npm run test` に含めた）| — |

候補はアプリの検索対象にしない。アプリは `data/sample-resources.json` だけを読む（テストで確認）。

### コマンド

```
npm run candidates -- collect [情報源ID ...]   # 一覧を取得して統合（既知の URL は取り直さない）
npm run candidates -- annotate                 # 取得せずに分類・振り分けを付け直す（reviews.json の反映）
npm run candidates -- report                   # 内訳と、深い確認の順番待ち
```

### 取得方法（汎用の3種類だけ）

| 種類 | 使った情報源 | 1件ごとの取得 |
|---|---|---|
| サイトマップ | lol-guide.com | 題名がサイトマップにないため、**未知の記事だけ**記事ページを1回取得（1秒間隔）|
| WordPress 公開 API | lolgaren.com | 不要（50件ずつ、題名・日付・抜粋・カテゴリ・本文の構成を一括取得）|
| YouTube チャンネルの動画一覧ページ | goru、Dopa English、Veigar v2 | 不要（1ページで新しい順に約30本）|

- 両サイトの robots.txt で、記事と API へのアクセスが許可されていることを確認した（2026-10-28）。
- YouTube の RSS（videos.xml）は、確認時に 404 を返したため使っていない。
- 動画はダウンロードせず、字幕も取得していない。
- 本文は保存しない。深さの推定のため、本文の**文字数と見出しの数**だけを記録する。抜粋は160字で切る。
  - （公開前の変更）抜粋は原典の説明文・書き出しそのものだったため、保存しないことにした。取得した抜粋は、分類に使う手がかり（excerpt_features）に変えてから捨てる（§11）。

### 候補の項目

既存の Resource と同じ名前の項目（url, title, type, language, creator, published_at, updated_at, duration_sec）に、候補用の項目を加えた。

| 項目 | 内容 |
|---|---|
| key / normalized_url / url_variants | 重複判定のキー（YouTube は動画 ID）、正規化 URL、見つけた表記ゆれ |
| sources / discovered_at / metadata_from | 発見元、最初に見つけた日（再実行で変えない）、メタデータの取得元 |
| excerpt_features / categories / structure / published_hint | 一覧で取れた手がかり（抜粋から取ったロール・Topic・理由／メンタル／学習の語の有無、サイトのカテゴリ・タグ、本文の文字数と見出し数、YouTube の「6年前」などの表記）。抜粋の文章は保存しない（§11）|
| roles / topic_ids / tier | 対象ロール・Topic 候補（既存 Topic の別名で照合）・優先区分（P1-common / P1-mid / P2 / P3 / unclassified）|
| depth_estimate / depth_signals | **深さの推定**（題名・抜粋・構成からの high / medium / low と、その根拠）|
| depth_confirmed | **本文を確認した深さ**（reviews.json にあるときだけ。ないときは null）|
| existing_resource_id / needs_review | 既存資料と同じ URL・動画なら、その ID。題名の類似・翻訳の可能性（確認が要る候補）|
| triage | 収録候補 / 保留 / 除外 / 登録済み、理由、判断者（rule = 規則、review = 個別確認）|

- 「深そう」（depth_estimate）と「深いことを確認した」（depth_confirmed）は、別の項目にした。
- 題名や見出しだけを見たものは、depth_confirmed に入れない。

### 重複の扱い

| 種類 | 扱い |
|---|---|
| 同じ URL、追跡パラメータ（utm_* など）・www・末尾の /・# だけ違う URL | 自動で1件にまとめる。違いは url_variants に残す |
| 同じ YouTube 動画（watch / youtu.be / shorts / embed）| 動画 ID で自動で1件にまとめる |
| 既存資料（登録済みの75件）と同じ | 「登録済み」にして、収録候補に数えない |
| 題名が似ている（文字 bigram の Jaccard 係数 0.6 以上）| **確認が必要な候補**として示すだけ。削除しない |
| 翻訳・字幕版の印がある動画（「日本語字幕」「ENG SUB」など）| 原典の特定が要る候補として示すだけ |
| 独立した資料が同じ結論 | 何もしない（重複ではない）|

## 3. 個別確認（16件）

代表として、収録候補から各区分・各深さの推定を選び、規則で保留にした「深さの推定が低い」2件も加えた。本文は scratchpad に取得して読み、リポジトリには保存していない。

| 資料 | 推定 | 確認した深さ | 確認の範囲 |
|---|---|---|---|
| ウェーブコントロールについて勘違いしがちなこと（lol-guide）| high | **deep** | 本文全体 |
| ウェーブを使った有利の作り方（lol-guide）| medium | **deep** | 5場面のうち1〜4 |
| ブラッドミアでアニビアに勝つ方法（lolgaren）| high | **deep** | 不利の理由・コンボ・ビルドとルーン |

| パワースパイクを理解しよう（lol-guide）| **low（保留）** | medium | 前半 |
| コントロールワードは買うべき？（lol-guide）| high | medium | 前半 |

| 通常攻撃を活かして勝利を握ろう（lol-guide）| medium | medium | 前半 |

| 3択以上は機能しない（lolgaren、自己啓発系）| medium | medium | 要所 |
| ミッドレーン初心者オススメチャンピオン5体（lol-guide）| medium | shallow | 見出しと選定基準 |
| シャットダウンゴールド、1コアまでの買い物術、毎日コツコツ、ドランシールド、ミッドゼラスのビルド | — | **未確定** | 冒頭と見出しだけ |

わかったこと：
- **深さの推定は、深さの順位付けには使えない**。推定 high の5件のうち deep は2件。推定 low で保留した2件は、deep と medium だった。
  - 原因：lol-guide は番号付きの段落を見出しタグにしていない記事があり、見出しの数や「理由」の見出しを数えられない。題名の語（「〜とは」「〜しよう」）も深さと関係が薄い。
- 除外の規則（別モード・サイト運営）は、確認した範囲では正しく働いた。
- **保留の規則は、深い教材を後回しにする危険が大きい**ことが、最終確認の抜き取り（§10）でわかった。当初の「保留の規則は役に立つ」という評価は、取り消す。
- 分類の誤りも見つかった。
  - 「ドランシールドは弱いのか」は、題名にロール名がなく、抜粋の「ミッド」で MID と推定したが、実際はトップ向け（P3）。
  - 抜粋で別モードに触れただけの記事を除外していたので、題名とカテゴリだけで判定するよう直した。
- 自己啓発系の「3択以上は機能しない」には、キーストーン・サモナースペル・スタートアイテムをプランA・Bに絞るという具体的な適用があった。今後の収録方針（Phase 4B の追補）どおり、収録候補として評価した。

## 4. 判断の部品（8件。実験メモであり、KnowledgeNote には登録していない）

本文を読んだ節からだけ抽出した。「原典」は資料の記述、「解釈」は AI の整理。

**E1. ウェーブの形は、主導権があるときにしか作れない**（res-lg-mmlgg「1. 最大の勘違い」）
- 状況：フリーズなど、望むウェーブの形を作りたい。
- 目的：ゴールド・経験値で差をつける。
- 選択：先にトレードの勝ち・相手のスキルの無駄撃ち・ミニオンを多く殴れる隙を作り、その後でウェーブの形を作る。
- 理由（原典）：相手も人間で、自分が弱ければ相手はミニオンを押し込んでフリーズを壊す。
- 代償：主導権がないまま形を作ろうとすると、押し込まれて逆に不利な形になる。
- 成立条件：体力有利・キル圧力・ガンクの脅威のいずれかがある。

**E2. 有利でも、常にフリーズが最善ではない**（res-lg-mmlgg「2.」）
- 状況：対面に勝っている。
- 選択：オブジェクトの前や、相手がロームしそうなときは、スロープッシュで大きなウェーブを押し付け、ダイブ・ワード設置・他レーンの援護に使う。
- 理由（原典）：フリーズ中はレーンから動けず、マップへの圧力とオブジェクトを失う。
- 代償：フリーズで奪えたはずのゴールド・経験値。
- 成立条件：オブジェクトの出現が近い、相手がファームを捨てて動く、味方ジャングラーが敵陣に入りたい。

**E3. フリーズの維持は「ラストヒットだけ」ではできない**（res-lg-mmlgg「3.」）
- 選択：敵ミニオンを自軍より3〜4体多く保つよう、相手がミニオンに与えたのと同じだけ削る。
- 理由（原典）：相手が押しているのにラストヒットだけだと、自軍ミニオンが先に全滅して、ウェーブがタワーに入る（フリーズが解ける）。
- 成立条件：自陣側で止める。差が小さすぎると、到着時間の差で解ける。
- 解釈：未解決だった「なぜこのウェーブを押してはいけないのか」に近いのは、同じ記事の「4. 中途半端な速いプッシュは、敵タワー手前で止まって相手にフリーズされる」。

**E4. チートリコール**（res-lg-dauwk「1.」）
- 状況：Lv1で主導権を取れた、または主導権のあるマッチアップ。
- 選択：1・2ウェーブはラストヒットだけでスロープッシュ、大砲の3ウェーブで押し込み、即リコール（約450ゴールド）。
- 理由（原典）：戻ったとき、自分はアイテム・体力・マナが有利で、ウェーブは跳ね返って自分側に来る。
- 代償：タワープレートの獲得や、主導権の維持を諦める。
- 成立条件：味方ジャングラーが逆側に向かう動線（蟹が湧く時間にウェーブが自分側に来るため）。主に上下レーンの戦術と書かれている。

**E5. 不利なときのプルからのフリーズ**（res-lg-dauwk「2.」）
- 状況：不利なマッチアップ、敵ジャングラーの位置が不明、自分のフラッシュがない。
- 選択：相手に押させ、自陣タワー手前で敵ミニオンを3〜4体多く保つ、または体で止める。
- 理由（原典）：タワー近くで安全にファームでき、相手はタワーから離れて CS を取ることになり、味方のガンクを受けやすくなる。
- 代償・注意：主導権がない、または味方ジャングラーの位置が知られていると押し切られ、跳ね返ったウェーブで危険が増す。
- 関係：Phase 4B の「劣勢時はウェーブを自陣側に保つ」（res-lg-kjumg、Dopa の TF 対フィズ）と同じ方向。kjumg は同じ著者なので、独立した裏付けとは数えない。

**E6. スプリットプッシュへの対応**（res-lg-lcwud 全体）
- 選択：タイマンで勝てるか時間を稼げるチャンピオンを当てる（同じレーンの担当でなくてよい）。または複数人でキャッチを狙う。止めにくければ、逆側のオブジェクトと交換する。
- 代償（原典）：対応したチャンピオンの分だけ、他のレーンのウェーブ処理や集団戦の力が落ちる。人数をかけすぎると、キルを取っても逆側のオブジェクトを取られる。
- 成立条件（原典）：相手のヴォイドグラブの数とタワーを折る速さを考える（1本のつもりが2本折られることがある）。

**E7. ブラッドミア対アニビアでは、倒すより「スロウのコンボにどう対処するか」**（res-garen-2610vladmia-anivia）
- 状況：ミッドのブラッドミアで、アニビアと対面（パッチ26.10の記事）。
- 理由（原典）：射程がわずかに長い、壁はプールでも抜けられない、パッシブで序盤のソロキルが難しい。アニビアのコンボは、後方に W → R → 逃げる方向に Q。
- 選択：標準のストームサージ型ではなく、ドランヘルム開始（Lv6まで AA と電撃を耐える）、シュレリアの戦歌（機動力）、征服者。
- 代償：標準ビルドの火力。
- 成立条件：このマッチアップとパッチ26.10の前提。記事中の統計（LOLALYTICS）は確認していない。

**E8. 選択肢は2つ（プランA・B）に絞る**（lolgaren「3択以上は機能しない」。登録していない）
- 選択：キーストーン、サモナースペル、スタートアイテムを、それぞれプランA・Bの2つに絞る（ミッドのブラッドミアの例）。
- 理由（原典）：選択肢が増えると「最善を選ばなければ」という圧力で判断が疲れる（著者は決断疲れの研究を引用している。研究そのものは確認していない）。
- 代償：まれな相手への最適解を捨てる。
- 成立条件：著者の経験則。ゲーム内では未検証。

### 検索評価の制約：文字列の一致は、質問への正しい回答を意味しない

- P04「レーンをフリーズしたいとき、なぜタワーの手前でミニオンを止めるの？」で、res-lg-mmlgg が「条件に一致」になった。
- 一致した「手前」は、資料では「（中途半端なプッシュが）**敵タワー手前**で止まる」という意味で、質問は**自陣タワー**の手前でフリーズする理由を聞いている。文字列は同じだが、指している場所は逆。
- 検索は語の文字列だけを比べ、語が何を指すか（自陣か敵陣か）、否定か肯定か、理由を聞いているかを区別しない。
- したがって「条件に一致」は「質問の語がすべて資料に現れた」という意味で、**質問に正しく答えている保証ではない**。評価の数値（到達・5位以内・1位）も、同じ制約の下での値。
- 今回は検索エンジンを変えない。判断理由の検索や AI 推論の段階で扱う課題として残す（Phase 4B の「なぜこのウェーブを押してはいけないのか」と同じ種類の問題）。

## 11. 公開前の変更：抜粋の文章を保存しない

- 確認したこと：
  - 候補データ（candidates.json）の excerpt には、364件中284件に、原典の文がそのまま入っていた。lol-guide の184件は記事ページの説明文、lolgaren の100件は WordPress の抜粋で、どちらも記事の書き出しと同じ文だった。合計で約4万字。独自に書いた要旨ではない。
  - 抜粋を使っていたのは、規則による分類と振り分けだけだった。具体的には、題名などにロール名がないときのロールの判定、Topic の照合、深さの推定の根拠「抜粋に理由・判断の語」、メンタル系・学習の語の判定。内訳・レビュー・登録の処理は使っていない。
  - 抜粋を単純に削ると、364件中142件の分類が変わり、36件は振り分けまで変わった。そのため、項目を削るだけにはしなかった。
- 変更：
  - 取得した抜粋は、統合の時点（lib.js の annotate）で、分類に使う手がかり（excerpt_features）に変えてから捨てる。手がかりの中身は、ロール、Topic、メイジかどうか、理由の語・メンタル系の語・学習の語の有無。
  - 分類と振り分けは、抜粋の文章ではなく手がかりを使う。
  - 既存の284件にも同じ変換を当てた。分類・振り分け・類似の判定は、変更前とすべて一致する（差異0件。Topic の並び順も同じ）。
- 再収集：既知の URL は取り直さない。新しく取得した抜粋も、保存の前に手がかりに変わる。抜粋の文章が候補データに戻ることはない（テストで確認）。
- 代償：分類の規則を変えても、保存済みの手がかりは、取得し直さない限り古い規則のまま。抜粋を使う規則を変えるときは、取得し直す必要がある。
