実施日：2026-11-01。基準コミット：`aba6bdb`。公開データ（`data/sample-resources.json`）は変更していない。

## A. 検索画面の「検索語に一致した知識ノート」

### 方式

- 資料の検索（`analyzeQuery`）は、Topic・発信者以外の残りの語を**公開資料の語彙**で採否する。そのため、ノートにしかない語（例：ヴォイドグラブ・コンディション・14分・攻撃範囲・ヘラルド）は捨てられる。
- `analyzeQuery` を2つの関数（`matchQueryUnits`＝Topic と発信者の取り出し、`splitResidualTerms`＝残りの語の分割）に分けた。資料の検索は同じ結果のまま（84件の検索の比較で一致）。
- ノートの照合（`src/data/noteSearch.ts`）は、Topic と発信者の取り出しを共有し、残りの語を**公開ノートの語彙**で採否する。新しい検索エンジンや外部サービスは使っていない。
- 対象は `isPublicNote` のノートだけ（散策・詳細と同じ条件）。
- 照合する箇所：主張・成立条件・例外・反証の条件・補足・時期の説明・根拠の要約・Topic の名前と別名、根拠の資料の発信者。
- 語ごとに、どこで一致したかを表示する（例：「ヴォイドグラブ」：主張）。
- 段：すべての条件に一致したもの（full）と、一部だけ一致した関連候補（partial、閉じた枠で控えめに表示）。
- 誤一致を減らす規則：
  - 大分類だけの検索（例：「マクロ」）では出さない。
  - 一部一致は、具体的な Topic に一致したときか、2つ以上の条件に一致したときだけ出す。
  - 日本語の複合語は、ノートの語彙にある2語に分けられるときだけ分ける（例：「タワープレート」→ タワー・プレート）。
- 旧仕様（`superseded`）のノートは、同じ段の後ろに並べる。

### 一致と回答の区別

- 一致したことは回答の保証ではないと明記する。否定・条件の向き・立場は判定しない。
- 検索語に否定の表現（ない・べきでない・not など）があれば、「向きを判定していない」と注意を出す。「避ける」は回避の意味なので否定に含めない。
- 語の一致が例外・反証の記述だけにあるときは、「主張と逆向き・限定の可能性」と印を付ける。
- カードに成立条件と例外を表示し、旧仕様・未検証の表示は散策と同じ `NoteSummary` を使う。

### 評価

`data/experiments/note-questions.json`（19問。`decision-questions.json` と同じ形に、`requires_cue`・`never`・`note_only_terms` を追加）。

- 19問すべて期待どおり（2回目の確認で29問）。答えのノートはすべての条件に一致し、先頭は答えか関連のノート。取り違えのノートは答えより前に出ない。
- **評価の範囲の注意**：評価用の質問は、公開ノート21件の内容を見て作ったもので、テストと同じ人（AI）が作っている。29問の成功は、この質問に対する回帰の確認であり、一般的な検索精度の保証ではない。
- ノートにしかない語：ヴォイドグラブ・14分・攻撃範囲・コンディションは、資料の検索では捨てられ、ノートの照合では使われる。
- 時期：「タワーのプレートは、今も14分で落ちる？」では、現行（26.1以降）のノートが旧仕様より前に出る。
- 条件の向き：「フリーズはタワーの攻撃範囲の中でする？」には、逆向きの主張（範囲の外）のノートが出る。主張をそのまま表示して読ませる。
- 否定：「フリーズしないほうがいいのはどんなとき？」に答える公開ノートはない。フリーズの場所のノートが語で一致するが、否定の注意を出す。
- 公開しないノート（kn-level2-minion-count・kn-level2-advantage・kn-offense-as-defense）は、どの検索にも出ない。
- 公開ノート21件すべてに、評価の質問か Topic の名前の検索で届く。

### 分かっている限界

- 「ガンクのルート」では、フラッシュの判断のノートが「ガンク」の語で一致する（ルートの答えではない）。語の一致だけでは避けられず、「一致は回答ではない」の表示に頼る。
- 否定の検出は文字列の規則で、「視界がないとき」のような状況の否定でも注意を出す（控えめな側に倒している）。
- 「オブジェクト前」の「前」のような1文字の語は使わない。

## C. 抽出記録（253件）からの下書き

### 方法

`tools/experiments/knowledge-drafts.js`

- `rows`：全行の件数と、原典ごとの正式資料の有無を出す。
- `draft 2:H15 …`：指定した行の下書きを作る。件数の上限はない。
- `check reviewed.json`：確認済みの下書きを作業用のコピーに入れ、既存の `validate` と追加の規則にかける。公開データは変更しない。

自動で写すもの：
- 原典の URL・著者・公開日とパッチ・候補キー、節（locator）、主張（記録の「知識」の列）、成立条件、関係の記述。
- 参照：既存ノート・判断材料・他の行。
- 印：相違・一致・同じ著者・古い・図未確認・仕様が未照合。

自動で決めないもの（review に理由を残す）：
- status は常に `unverified`、確認レベルは空のままにする（昇格させない）。
- kind と topic_ids は提案だけ（Topic は記述に名前・別名が現れたもの）。
- 正式資料は URL で照合するだけで、未登録の原典は登録しない（`resource_id` は null）。
- 統合するかどうか：「相違・条件の違い」があれば「無条件に統合しない」、同じ資料の根拠を持つ既存ノートがあれば「登録済みでないか確かめる」と示す。

`check` の規則：
- 確認者（`reviewed_by`）がいること。
- 根拠の資料が正式資料であること。
- evidence_type・確認レベル・kind・topic_ids が決まっていること。
- status を上げるには `status_approved_by` が要る。
- 同じ主張のノートや、同じノート・同じ資料の根拠は二重に登録しない。
- 関係（relations）も追加できる。最後に既存の `validate` にかける。

#### operations の形式（2026-11-08 追加）

ローム収録のパイロット（`roaming-intake-pilot.md`）で使い捨てのスクリプトで補った判断を、`check` で書いて検証できるようにした。旧形式（`decision.action`）の動作・エラー文は変えていない。

- 1行の `decision` に `operations`（配列）を書くと、書いた順に実行する。操作は `new_note`・`add_evidence`・`annotate_note`・`merged`・`skip` だけで、ほかはエラー。
- **統合**：統合先の行の `new_note` に `merges_rows` と `merge_reason_ja`、統合元の行に `merged`（`into`・`reason_ja`）を書く。両側の宣言が一致しないとエラー。統合元の成立条件が統合先の成立条件・例外・補足にないときは、`conditions_handling_ja` に扱いを書かないとエラー（主張は合成しない）。
- **1行から複数の操作・分割**：1行に `new_note` を複数、または `new_note` と `add_evidence` を並べられる。
- **複数の根拠**：`new_note` の `evidence` は配列。1件目だけが行の下書きの根拠（資料・節・要約）を引き継ぐ。別の資料の根拠や2件目以降は、id・resource_id・locator・summary_ja をすべて書く（行の原典の値を別の資料に引き継がない）。同じ資料・同じ位置の根拠の重複はエラー。別の原典を独立した裏付けとは判定しない（補足に人が書く）。
- **関係**：`{ to, type }`（このノートから）か、`{ from, to, type }`（既存ノートからこのノートへ、など）。このノートを含まない関係、7種以外の種類、存在しない参照先、自分自身への関係、同じ関係の重複はエラー。関係は全操作の後に確かめるので、同じ一括の後の行で作るノートを参照できる。
- **既存ノートの補足**：`annotate_note` は `notes_ja` と `source_person` への追記だけ。ほかの欄を書くとエラー（主張・status・確認レベルは変えられない）。
- `add_evidence` の二重登録（同じノート・同じ資料）は、旧形式では報告して飛ばすが、operations ではエラー（別の箇所なら `allow_same_resource` を明示）。
- 実行順の制約：`add_evidence`・`annotate_note` の対象は、既存ノートか、それより前の操作で作ったノートだけ。
- 結果の `pending_human_review` に、`reviewed_by`・`status_approved_by` が「人の確認待ち」などの値の行を返す。文字列があることを人の承認とは扱わない（エラーにはしないが、正式に登録する前に人が確かめる）。
- テストなどで中身を確かめるときは、`check(reviewed, data, { withCopy: true })` で検証に使った作業用のコピーを結果の `copy` に含められる（CLI の出力には含めない）。
- `check` は公開データを変えない。作業用のコピーで検証するだけで、正式データへの反映は今も別の手作業（`check` が通った内容を人が `data/sample-resources.json` に書く）。

| タワー下での戦い方 | ノートなし（「タワー下」を照合に使わない） | 取りこぼしではない（公開ノートに該当がない）。複合語の分割は、両方の語がノートにあるときだけ |
| ジャングラーの位置がわからないとき | kn-trade-on-key-cd（例外に「敵ジャングラーの位置が不明」） | 例外の記述での一致。否定・条件の注意は出る |
| Lv1のトレード | 一部一致の関連候補が7件 | **誤った関連候補が多い**。「Lv1」を「レベル1」と読み、経験値の Topic とトレードの Topic の片方だけに一致したもの。閉じた枠に出るので控えめだが、雑音になる |
| 相手のスキルが上がっているときは引く | kn-trade-on-key-cd・kn-trade-window-6-8s が完全一致 | **前提の逆転**（ノートは「スキルが CD 中なら仕掛ける」）。N20 と同じ型の限界で、条件の注意だけが出る |
| 視界の取り方 | 2013〜2014年のワードのノート2件が先頭 | **時期の注意**。現行での適用が unknown のノートは、superseded と違い後ろに回さない。カードに時期は表示される |

### 限界の種類

| 種類 | 例 | 原因 | 影響 |
|---|---|---|---|
| A. 前提・条件の逆転 | 相手のスキルが上がっているときは引く、フラッシュがある相手に仕掛けるべき？（N20） | 検索ロジック：語は一致するが、状態の向き（上がっている／CD 中）を照合しない | 大きい。完全一致として出て、条件の注意しか出ない |
| B. 一部一致の候補の雑音 | Lv1のトレード | 検索ロジック：2つの Topic の片方だけの一致を関連候補にする | 小さい。閉じた関連候補の枠に出る |
| C. 過去の知識が上位に出る | 視界の取り方 | 検索ロジック：並び順を下げるのは superseded だけで、時期が unknown の古い知識は下げない | 中程度。カードに時期は出るが、現行の攻略法を探す人には適切な順ではない |
| D. 語彙不足・検索漏れ | タワー下での戦い方、ゾーニャの使いどころ | **収録知識の不足**（検索ロジックの失敗ではない）：該当する公開ノートがない | 知識を収録すれば解消する。チャンピオン研究（ゾーニャ）・抽出記録（タワーダイブ）に候補がある |
| E. 例外の部分だけの一致 | ジャングラーの位置がわからないとき | 検索ロジック：kn-trade-on-key-cd の例外（敵ジャングラーの位置が不明）に、Topic の名前で一致する。逆向きの印は語の一致だけを対象にしており、Topic の一致には付かない | 中程度。そのノートは質問の答えではなく「適用してはいけない条件」の側。カードの例外の表示で読み分ける必要がある |

- これらは記録にとどめ、今回は実装を変えていない（大規模な変更を避けるため）。
- 次に直すなら、前提の逆転（N20 と同じ型）が最も影響が大きい。主張・成立条件に含まれる状態の語（CD 中・落ちている・ない）と、検索語の状態の語（上がっている・ある）の対を、少数の規則で照合する方法が候補。
