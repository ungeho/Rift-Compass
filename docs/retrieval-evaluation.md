# 検索方式の比較（机上評価）

> **注意**：Phase 0 では検索エンジンを実装していません。以下は **検索順位の測定ではありません**。サンプルデータ38件に対して、「質問の検索語が、各方式で参照するフィールドに現れるか」を照合しただけの到達可否チェックです。

## 1. 比較する方式

| 方式 | 参照するフィールド |
|---|---|
| T（参考） | `title` のみ |
| **A** | `title` ＋ 発信者名 ＋ Topic の表示名（`label_ja` / `label_en`）|
| **B** | A ＋ `summary_ja` ＋ Topic の別名（`aliases_ja` / `aliases_en`）|
| **C** | B ＋ 動画の `segments` のラベル ＋ その Resource を根拠とする KnowledgeNote の本文 |

## 2. 照合の方法

- 質問ごとに、作業者（AI）が検索語のグループを決めました（例：Q01 は「仕掛け／トレード／trade」**かつ**「CD／クールダウン／cooldown／スキルが落ち」）。
- 各方式のフィールドを連結した文字列に、すべてのグループのいずれかの語が含まれる（大文字・小文字は区別しない）資料を「到達可能」としました。
- 「期待資料」は、資料の内容を踏まえて作業者（AI）が事前に決めたものです。レビュー反映で資料を1件（Patch 26.1 Notes）追加しましたが、期待資料は変えていません。

### 再現方法

照合スクリプトをリポジトリに含めました。依存パッケージは不要です（Node.js のみ）。

```
node tools/desk-retrieval-check.js
```

- 質問・検索語・期待資料はスクリプト内の配列 `Q` に定義しています。
- 出力の各セルは「期待資料のうち到達できた数/期待数 (到達可能と判定された資料の総数)」です。
- 2026-10-27 に資料38件で実行した結果を、4章に記載しています。
- これは参考用の机上チェックです。Phase 1 では、検索の実装と同じコードを使い、順位まで評価できる再現可能なテスト（固定の質問セットと期待資料、第三者が作成した質問を含む）に置き換えます。

### この評価の限界（重要）

1. **質問・検索語・Topic の別名・期待資料を、同じ作業者（AI）が作っています**。別名が質問に合わせて作られているため、B の結果は実際より良く出ています。
2. 日本語の形態素解析・表記ゆれ（「タゲ」「ターゲット」）・誤字・言い換えを扱っていません。
3. 順位を見ていないため、C の「該当件数が多い」ことが、良いこと（網羅）なのか悪いこと（ノイズ）なのかは判断できません。
4. 資料は38件しかありません。

## 5. 机上で確認できたこと

1. **タイトルだけ（T）では、日本語の質問にほとんど届かない**。資料の大半は英語タイトルで、日本語の質問（Q01、Q02、Q06 など）はタイトルとまったく一致しません。
2. **Topic の表示名を加えるだけ（A）で、日英の橋渡しの大部分ができる**（13 → 31）。Topic を人が正しく付けることが前提です。
3. **別名と日本語紹介文（B）で、俗語・略語・言い換えに届く**（31 → 37）。差が出たのは「AA無効化」（Q09）、「イグナイト／バリア」（Q12）、「フラッシュ」（Q14）、「トリンケット」（Q15）、「level 2 … minions」（Q03）です。
4. **C は到達件数を増やさないが、答えの粒度を変える**。期待資料への到達は B と同じでしたが、Q05 では「動画のどこか」ではなく「19:18 から」と答えられます。一方、Q09（3 → 7件）や Q23（6 → 10件）では、該当件数が増えてノイズになりうることも分かりました。
5. **Q01 では Wiki Cooldown に届かなかった**。AND条件（「仕掛け」かつ「CD」）を満たさないためです。仕様の資料は、判断の質問には直接一致しません。KnowledgeNote の Relation（`reason_for`）を辿って補う必要があります。
6. **該当なし（Q04）を返せること**も、データ上は確認できました。ただし実際の検索で「関係の薄い資料を上位に出さない」ことは、順位付けがないと確認できません。

## 7. 推奨

- 初期実装は **方式B（タイトル＋Topic＋別名＋日本語紹介文）** を基本にします。
- **C は「区間へのリンク」と「Note 経由の関連資料」に限定** して使い、全文一致の対象にはしません。
- 評価では、第三者（実際のプレイヤー）が書いた質問を30問以上集め、作業者が期待資料を決める前に質問を固定します。

## 8. Phase 1 の実装による実測（2026-10-27）

Phase 1 で実装したクライアントサイド検索（`src/search/search.ts`）で、同じ24問を実行した結果です。机上照合と違い、**実際の順位** を記録しています。机上評価の到達数（37/38）は合格基準にしていません。

### 実装した検索の仕様

- 対象は方式Bと同じです（タイトル・発信者名・日本語紹介文・Topic の日英表示名と別名）。知識ノート本文と動画区間は使いません。
- 入力を Unicode 正規化（NFKC）し、小文字化と空白の整理をします。
- 入力から Topic の別名と発信者名を **長い一致から順に重ならないように** 抜き出し、それぞれを1つの「概念」とします。
  - 空白の有無は問いません（「level 2」と「level2」、「Veigar v2」と「VeigarV2」）。英字だけの語は単語の途中では一致させず、複数形の s は許容します。
  - 1文字の別名（Topic「リコール」の別名「B」）は誤一致が多いため使いません。
- 残った部分は、日本語ならひらがな（助詞・送り仮名・活用語尾）で区切り、漢字・カタカナ・英数字の並びを語にします（例：「いつ導入された」→「導入」）。一般的な語（「知りたい」「方法」「知識」「lol」など）と1文字の語は除きます。**資料中に一度も現れない語は使わず、「検索条件に含めなかった語」として画面に表示します。**
- 概念は「具体的」と「一般的」に分けます。一般的な概念は、大分類の Topic（例：lane → レーニング）と、公開資料の1/4を超えて現れる語（例：スキル）です。
- 結果は3段階に分けます（実装：`MatchKind`）。
  - **条件に一致（full）**：具体的な概念にすべて一致し、検索条件に含めなかった語がない。一般的な概念は必須にせず、一致すれば順位を上げるだけです（具体的な概念がない検索では、全概念を必須にします）。
  - **認識できた条件に一致（recognized）**：具体的な概念にはすべて一致したが、資料中にない語が残っている。画面では、その語を条件に含めていないこと、その語について扱っているとは限らないことを明示します。「条件に一致」の件数には数えません。
  - **関連候補（partial）**：具体的な概念の一部にだけ一致した。主一覧とは別の欄に、一致した条件ごとにまとめて表示します。条件に一致する資料があるときは、この欄を閉じた状態で表示します。一般的な概念だけに一致した資料は候補にしません。
- 並び順：条件に一致（または認識できた条件に一致）を先にし、一致数と重みの合計で並べます。関連候補は、より具体的な概念（発信者 > Topic > 語）に一致したものを先にします。
  - 重みは次のとおりです：Topic の直接一致 10（大分類は 4）、下位 Topic での一致 6（大分類は 3）、別名そのものがタイトルか紹介文にあれば +3、発信者本人 12、発信者名がタイトル・紹介文にある第三者の資料 6、語の一致はタイトル 6・発信者名 8・Topic 名 5・紹介文 3。語の重みは、現れる資料数が3以下なら1倍、資料の1/4以下なら0.7倍、それを超えれば0.4倍にします。
- 資料中にない語（主題とみられる語）があり、認識できたのが語だけ（Topic・発信者なし）の場合は0件にします（例：「ドラゴンソウルの効果」で「効果」だけを根拠に出さない）。
- 通常の公開対象（`access.free === true` かつ L2 以上、36件）だけを検索します。

> 初版（レビュー前）は「概念の過半に一致した資料を候補にする」と説明していましたが、実装は `Math.ceil(units.length / 2)` で、2概念のとき1概念で通過していました。また、未知語を無視したまま「全語一致」と判定していました。レビューを受けて、上の3段階に改めました。

### 修正による変化の内訳

- **良くなった**：Q23・Q24 が条件に一致して1位になりました。Q10・Q17 では、大分類「lane」だけに一致した候補（11件・16件）がなくなりました。Q15 は「導入」、Q20 は「追跡」を語として拾えるようになりました。
- **区分が変わった（順位は維持）**：
